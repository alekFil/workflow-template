# workflow-template — Decisions (ADR)

> Курируемые архитектурные решения. Пополняются командой `/record`.
> Порог для записи — 4-пункт чек-лист (см. ADR-026). Мелкие фиксы, переименования, cleanup живут в commit-сообщениях, не здесь.
> Заменённые и отклонённые ADR переносятся в `.context/history/decisions/<year>.md` (год написания). В активном срезе — только текущие решения.

## ADR-031: Skill boundaries — команда не исполняет соседний скилл автоматически

**Статус:** Принято

**Контекст:** Ретроспектива 2026-08-31 выявила устойчивый паттерн: модель регулярно расширяет исполняемый скилл шагами из соседнего. Конкретный триггер — `/dev` по скиллу должен заканчиваться отчётом, но фактически предлагал commit-сообщение и просил подтверждения, де-факто частично исполняя `/commit` без явного вызова. Пользователь заметил, паттерн шёл незаметно много task-циклов. Приоритет 4 в to-do был реакцией на этот конкретный случай, но проблема шире `/dev` — потенциально касается всех скиллов (`/architect` может «заодно» реализовать; `/close` при uncommitted изменениях может «заодно» `/commit`; `/report` может «заодно» коммитнуть).

**Решение:**

1. **Строгое правило:** каждый скилл завершается строго в своих границах и не выполняет действия, находящиеся в scope другого скилла.
2. **Мягкая формулировка:** подсказать следующий шаг в тексте («Commit? (`/commit`)», «Готово к `/close`») — допустимо и полезно. Автоматически исполнить его — нет.
3. **Место фиксации:** новый раздел «Skill boundaries» в `CLAUDE.md` обоих слоёв — единый источник правды, короткое правило + пример.
4. **Enforcement:** правило в скилле, исполнение на модели (soft enforcement). Будущее направление — миграция на hooks (Stop-хук или per-command), но это отдельная задача, вне scope этой ADR.
5. **Замещает Приоритет 4 в to-do** («устранить `/dev` → авто-commit») — этот пункт был частным случаем; правило теперь общее.

**Отвергнутые альтернативы:**

- **B. Точечная правка каждого командного файла** (11 файлов, дублирование правила): при добавлении нового скилла легко забыть; нет единого «почему»; правило рассеяно.
- **C. Гибрид — правило в `CLAUDE.md` без ADR + ссылки из `commands/`:** не проходит через архитектурный корпус, теряется как справочный контекст при онбординге; commit-message-уровень для системного правила слишком тонкий носитель.
- **Автоматическое исполнение с явным приглашением** («предлагаю commit, ok?»): субъективно удобно, но регулярно приводит к нарушению контроля пользователя и размытию границ. Дисциплина «строго не сползать» снимает целый класс ошибок.

**Последствия:**

- `CLAUDE.md` обоих слоёв получает новый раздел «Skill boundaries» с правилом и коротким примером (допустимая подсказка vs недопустимое исполнение).
- `.claude/commands/dev.md` в обоих слоях — уточнить: «After completion, report only. Do not propose commit messages or invoke /commit».
- Симметрично проверить `.claude/commands/architect.md`, `.claude/commands/close.md`, `.claude/commands/report.md`, `.claude/commands/sync.md` на аналогичные зоны сползания.
- Приоритет 4 в `to-do.md` («устранить `/dev` → авто-commit») закрывается как замещённый этим ADR.
- Enforcement — soft (правило в тексте скилла + дисциплина модели). Hard enforcement через hooks — отдельная задача backlog.

## ADR-030: `plan.md` как task-local — жизненный цикл и классификация артефактов по scope

**Статус:** Принято

**Контекст:** `.context/plan.md` до сих пор жил на всех ветках — на `main`, `dev`, `feature/*`. Фактически используется как task-local: пишется под конкретную задачу, чистится/переписывается под следующую. Для соло-разработки это работает — одна активная задача одновременно, `plan.md` на `dev` всегда актуален для «того, что делаем сейчас». Для команды ломается:

- Dev A стартует `/architect` на `feature/foo` → пишет `plan.md` этой задачи.
- Dev B параллельно стартует `feature/bar` → пишет свой `plan.md`.
- При merge feature-веток в `dev` — `plan.md` конфликтует или одна ветка перезатирает другую.
- На `dev` вопрос «что за план сейчас?» становится бессмысленным — планов может быть N.

Проблема глубже эргономики: `plan.md` в шаблоне *семантически* task-local (относится к одной задаче), но *технически* project-wide (лежит в общем каталоге, шаг за шагом коммитится). Расхождение семантики и техники — источник багов.

**Решение:** Явное разделение артефактов по scope + жизненный цикл `plan.md`.

1. **Три уровня scope для артефактов `.context/`:**
   - **Project-wide** — живут на всех ветках, синхронизируются через merges: `product.md` (если появится), `blueprint.md`, `status.md`, `to-do.md`, `decisions.md`, `discussions/`, `history/decisions/`, `history/retros/`, `.claude/`, `CLAUDE.md`, `WORKFLOW.md`.
   - **Task-local** — существуют только на `feature/*`, исчезают при `/close`: **`plan.md`** (единственный представитель этого класса).
   - **Private** — не в git, не ветвится, локально у мейнтейнера: `notes/`.

2. **Жизненный цикл `plan.md`:**
   - **На `main`/`dev`:** файла нет (полное отсутствие, не пустая заглушка). Отсутствие сигнализирует «нет активной задачи».
   - **`/architect` и `/next`:** ветка нужна *только в момент записи `plan.md`*, не при старте режима. Обсуждение без записи плана валидно без ветки. При попытке записать `plan.md` вне `feature/*` — задаётся вопрос «на feature-ветке? если нет, создать?». Автоматика не применяется — пользователь может обсуждать абстракцию без намерения реализовывать.
   - **`/close`:** отдельным коммитом `chore: clean plan.md` удаляет `plan.md` на feature-ветке *до* ff-merge. `dev` остаётся чистым by construction.

3. **Ретроактив:** текущий `plan.md` на `dev` (завершённый по ADR-029) удаляется в рамках реализации этой ADR. Иначе `dev` нарушает принятое правило с первого дня.

4. **Шаблонный слой:** `template/.context/plan.md` удаляется. Новый проект стартует без активных задач; `plan.md` появится при первом `/architect → feature/*`.

5. **Скиллы обновляются в обоих слоях:**
   - `cc-architect-sync.md` — отсутствие `plan.md` на `main`/`dev` больше не ошибка, а норма; убрать чек про наличие; при обнаружении `plan.md` на защищённой ветке — сигнализировать «правило нарушено, plan.md должен быть удалён `/close`-ом».
   - `cc-close-task.md` — добавить шаг «удалить `plan.md` отдельным commit'ом до rebase/merge».
   - `.claude/commands/architect.md` и `.claude/commands/next.md` — упомянуть правило branch-check перед записью.
   - `CLAUDE.md` обоих слоёв — раздел «Artifact scope» с явной классификацией.

**Отвергнутые альтернативы:**

- **Пустая заглушка на `dev`/`main`** — половинчатое решение. Файл есть, но пустой → возникает вопрос «зачем он», лишний шум в дереве. Явное отсутствие честнее и симметричнее other-task-local-концепциям (например, git worktree — нет ветки, нет файлов).
- **Автоматически создавать feature-ветку при `/architect`** — риск случайного создания веток для абстрактных обсуждений или разбора чужого кода. Явный вопрос сохраняет контроль пользователю.
- **Удалять `plan.md` на `dev` после merge** — та же цель достигается, но история менее самодокументируема (нет коммита «задача закрыта, план вычищен» рядом с самой задачей).
- **Оставить как есть, принять что для команды сломано** — противоречит цели: шаблон предназначен для использования в проектах, включая командные; поломка при переходе соло→команда — известный failure mode, не поправить сейчас — платить каждой командой отдельно.

**Последствия:**

- `plan.md` перестаёт быть источником merge-конфликтов в команде.
- На `dev` можно смотреть `git status`/`ls .context/` и однозначно видеть «нет активной задачи».
- Каждая feature-ветка самодостаточна: содержит и код, и план в одном месте, живёт независимо.
- `template/.context/plan.md` уходит; при развёртывании через `install.sh` новый проект получает пустое `.context/` (в части `plan.md`).
- CLAUDE.md обоих слоёв получает раздел «Artifact scope» — явную классификацию, служит справочником при добавлении новых артефактов в будущем (проверить: project-wide? task-local? private?).
- Скиллы `/architect`, `/next`, `/close`, `cc-architect-sync` обновляются в обоих слоях.
- Правило fail-loud: если пользователь по ошибке не удалил `plan.md` перед merge — при следующей параллельной feature-задаче он получит merge-конфликт, что заставит вспомнить правило. Без невидимой деградации.

## ADR-029: Three-way split — notes / discussions / history-retros

**Статус:** Принято

**Контекст:** `.context/discussions/` использовался как единая свалка: pre-ADR думание с ассистентом, открытые идеи, retro-output, post-hoc summary решений. Все — committed, попадали в git и грузились в контекст CC. По факту это раздутый контекст, потому что большая часть содержимого — «черновики думания» одного человека с AI, а не согласованные командные документы. При этом всё лежит в общей директории, семантика перепутана.

Параллельно существовал `.context/notes/` (ADR-011: private, `.gitignore`) — концептуальная посадочная площадка для личного, но по факту заброшенная в пользу discussions/.

Retro (`retro-*.md`) — формально shared артефакт (output `/retro`-скилла) — тоже лежал в discussions/, хотя семантически ближе к историческому архиву, чем к активному обсуждению.

**Решение:** Three-way split по семантике источника и режима видимости.

1. **`.context/notes/`** — private (`.gitignore`, уже так). Место для всего, что рождается в диалоге с ассистентом: pre-ADR думание, черновики, открытые идеи, post-hoc summary. Не грузится в контекст, не публикуется, локальная копия только у владельца.

2. **`.context/discussions/`** — committed, но только для **внутрикомандных human-to-human обсуждений**. Не для AI-диалогов. Для соло-проекта — обычно пустая директория (`.gitkeep`-стаб). В шаблонном слое сохраняется как слот для команд.

3. **`.context/history/retros/`** — новая директория. Committed, содержит output `/retro`-скилла: `history/retros/YYYY-MM-DD.md` (без префикса `retro-`, потому что папка уже говорит «что это»; формат согласован с `history/decisions/`). Каждый ретро — отдельный файл (не накопительный, в отличие от decisions — независимые события).

4. **Ретроактив:** правило применяется к существующим 5 файлам:
   - `retro-2026-06-21.md` → `git mv` в `history/retros/2026-06-21.md` (в git остаётся).
   - `2026-06-08-install-and-mini.md`, `2026-06-08-mini-claude-md-design.md`, `2026-06-18-local-llm-agent.md`, `2026-08-30-adr-discipline.md` → `git mv` в `.context/notes/`. Так как `notes/` в `.gitignore`, git видит источник как удалённый, а копия остаётся у мейнтейнера локально. Правило применяется буквально: «эти файлы должны были быть в notes/».

5. **Скиллы:** `cc-retrospective.md` в обоих слоях переводится с записи в `.context/discussions/retro-*.md` на `.context/history/retros/YYYY-MM-DD.md`.

6. **`CLAUDE.md` обоих слоёв:** Components-строка про `.context/` актуализируется — упоминает `discussions` (team), `history/decisions` (archived ADRs), `history/retros` (archived retros).

7. **Открытая идея о local LLM agent** — уходит в notes/ вместе с файлом. Отдельно фиксировать в `to-do.md`/`blueprint.md` не будем: идея не созрела до продуктового статуса; если созреет — оформится ADR обычным путём.

**Отвергнутые альтернативы:**

- **`.claudeignore` для `discussions/`** — маскирует симптом (утечку контекста), не решает проблему (мусор в repo + смешение семантик).
- **Оставить всё как есть, применять правило только к новым файлам** — оставляет 5 legacy-файлов раздутым контекстом; правило без ретроактивного применения теряет ~половину эффекта.
- **`git rm` четырёх AI-файлов** вместо `git mv` в notes/ — жёстче без выгоды: локальная копия у мейнтейнера ценна как личный след; в git-истории всё равно останется.
- **Retro в discussions/** — конфликтует с назначением discussions/ (командное), и семантически ретро — исторический артефакт, ближе к history/.

**Последствия:**

- `.context/discussions/` в мейнтейнерском слое становится пустой (`.gitkeep`). В шаблонном слое уже такая.
- 4 AI-файла пропадают из git-истории будущих клонов (сохраняются в git log до текущей точки).
- 1 retro переезжает: путь `history/retros/2026-06-21.md`.
- `cc-retrospective.md` обновляется в обоих слоях.
- `CLAUDE.md` (root + template) — Components-строка `.context/`.
- Директория `.context/history/retros/` создаётся; `.gitkeep` не нужен (сразу с содержимым).
- Соло-мейнтейнер продолжает вести черновое думание в `notes/` — то, что фактически уже делал в discussions/, но с правильной приватностью.
- Разделение по семантике источника фиксировано: AI vs team vs archived.

## ADR-028: Разделение логической карты (CLAUDE.md) и физического дерева (status.md)

**Статус:** Принято

**Контекст:** `CLAUDE.md` (root) содержал блок «Repo structure» — файловое дерево с папками и файлами и пояснениями. `.context/status.md` содержит «Структура проекта» — то же файловое дерево, auto-generated при `/report`. Симметрично в шаблонном слое: `template/CLAUDE.md` держал плейсхолдерное дерево `{PROJECT_STRUCTURE}`, `template/.context/status.md` — плейсхолдер физического дерева. Три проблемы:

- **Дублирование.** Одна и та же информация в двух местах — тратится место в контексте CC и внимание мейнтейнера.
- **Дрейф.** Ручной блок в `CLAUDE.md` уже отстал: не упоминает `cc-code-polish.md` и `cc-retrospective.md`, хотя оба существуют. Ручные деревья устаревают без ошибок в CI — тихо и незаметно.
- **Смешение уровней.** Файловое дерево (что реально лежит) и логическая карта (какой компонент за что отвечает) — разные артефакты с разным жизненным циклом.

**Решение:** Разделить по abstraction level.

1. **`CLAUDE.md` — логическая карта компонентов.** Блок «Repo structure» с деревом заменяется на «Components»: одна строка на компонент, без файлов, без ASCII-веток. Пример для мейнтейнерского слоя:

   ```markdown
   ## Components

   - `.claude/` — CC tooling (index, commands, meta-skills, project rules)
   - `.context/` — workflow artifacts (blueprint, plan, to-do, status, decisions, discussions, history/decisions)
   - `scripts/` — user-facing installers (install/uninstall via curl)
   - `template/` — payload deployed into new projects
   - Top-level: CLAUDE.md, CONTRIBUTION.md, SETUP.md, README.md, LICENSE
   ```

2. **`.context/status.md` — физическое дерево.** Как есть, auto-generated при `/report`. Не трогаем.

3. **Шаблонный слой симметрично.** `template/CLAUDE.md` получает «Components», полностью схематичный: `.claude/` и `.context/` фиксированы, остальное — один плейсхолдер `{PROJECT_LAYOUT}` для проекто-специфичных областей. Пользователь заполняет `{PROJECT_LAYOUT}` при первичной настройке одной-двумя строками верхнего уровня. `template/.context/status.md` — не трогаем.

4. **Плейсхолдер `{PROJECT_STRUCTURE}` (существовавший в `template/CLAUDE.md`) отпадает.** Если он документирован в `template/WORKFLOW.md` как placeholder для пользователя — заменяется на `{PROJECT_LAYOUT}` или снимается.

**Отвергнутые альтернативы:**

- **Только в `CLAUDE.md` (дерево + карта в одном).** Решает дублирование, но дрейф остаётся (даже усугубляется — всё в одном месте, никто не сверяется с реальностью). Провалено уже на практике.
- **Только в `status.md` (без представления в `CLAUDE.md`).** CC загружает `CLAUDE.md` каждой сессии; без даже общего «что здесь есть» CC вынужден дочитывать `status.md` для базового ориентирования. Дороже.
- **Ничего, использовать `tree`/`ls` по запросу.** Ноль дрейфа, но CC получает шум (нерелевантные файлы, отсутствие пояснений), а человек-читатель `CLAUDE.md` вообще ничего не видит.

**Последствия:**

- `CLAUDE.md` (root) и `template/CLAUDE.md` теряют блоки с деревьями, получают компактные «Components». Файлы становятся легче (~20 строк экономии в каждом).
- `.context/status.md` и `template/.context/status.md` — без изменений.
- Плейсхолдер `{PROJECT_STRUCTURE}` в шаблонном слое отпадает; при наличии в `template/WORKFLOW.md` — обновляется/снимается.
- Дрейф исключён by construction: физическое дерево auto-generated, логическая карта редко-меняющаяся и человеко-читаемая; расхождения ловятся глазом при `/report`.
- Внешние ссылки «см. блок Repo structure» (если есть в других файлах) — обновляются в рамках задачи.

## ADR-027: Убрать file-архив status.md — перезапись без снапшотов + git-указатель

**Статус:** Принято

**Контекст:** `.context/history/{N}-status-*.md` накопил 14 файлов snapshots (001–014, ~150 KB). Никто их не читает: rediscovery-запросы отсутствуют, ретроспектива использует `/retro` (git log + decisions.md), долгосрочная эволюция описана в decisions.md. При этом `.claudeignore` для их скрытия из контекста CC не создан (Приоритет 3 to-do) — файлы утекают в auto-load. Заявленная цель (`archive → excluded via .claudeignore, read on request`) не реализована и по существу не нужна: git-история `status.md` уже содержит эволюцию через `git log -p -- .context/status.md`.

**Решение:**

1. **Отказаться от file-архива `status.md`.** `/report` больше не создаёт `.context/history/{N}-status-*.md`. Прошлые снапшоты доступны через git-историю: `git show <commit>:.context/status.md`.
2. **Удалить существующие 14 архивных файлов** и `.context/history/.gitkeep` (директория теперь непустая — содержит `decisions/`).
3. **Git-указатель в новом `status.md`.** При каждом `/report` — первая строка после заголовка и даты имеет вид:

   ```markdown
   > Previous state: commit <shortsha> (<YYYY-MM-DD>)
   ```

   `<shortsha>` — 7-символьный хэш, `<date>` — дата коммита. Источник — `git log -1 --format='%h %ai' -- .context/status.md`, взятый *до* overwrite'а. Ретрофит текущего `status.md`: pointer добавляется в рамках этой задачи, указывает на актуальный на момент реализации commit.
4. **Затрагивается только status-архив.** `.context/history/decisions/<year>.md` не трогаем — активные ADR ссылаются на него по конвенции `(archived, see history/decisions/YYYY.md)` из ADR-026. Иной вид истории.
5. **Скилл `cc-status-report.md` упрощается в обоих слоях:** убираются step 1 (архивация с нумерацией) и секция «Working with the history archive» — становятся неактуальными; добавляется шаг захвата предыдущего commit'а и вставки pointer-строки.

**Отвергнутые альтернативы:**

- **Rolling window (последние N снапшотов):** не отвечает на «зачем вообще?». Если 0 читателей — 3 файла или 14 равнозначно бесполезны.
- **Оставить как есть + добавить `.claudeignore`:** маскирует симптом (утечку), не решает проблему (мусор в репо, накладные расходы на архивацию в `/report`).
- **Не писать `status.md` вообще, собирать «на лету»:** пропадает snapshot-документ, на который ссылаются `cc-architect-sync.md` и другие скиллы. Слишком радикально.

**Последствия:**

- `cc-status-report.md` в обоих слоях упрощается: минус шаг архивации, минус секция «Working with the history archive», плюс шаг захвата предыдущего commit'а и вставки pointer-строки.
- Удаляются 14 файлов `.context/history/{N}-status-*.md` и `.context/history/.gitkeep`.
- Задача Приоритета 3 to-do про `.claudeignore` для `.context/history/` становится неактуальной: после удаления status-архива в `history/` остаётся только `decisions/`, и его CC должен читать (не скрывать). Задача снимается.
- `template/.context/history/.gitkeep` сохраняется — шаблонный слой начинает с пустой структуры для нового проекта.
- Единый формат `status.md`: каждый файл содержит pointer на предыдущую версию, включая текущий (ретрофит).

## ADR-026: Дисциплина ADR — двухуровневая модель, чек-лист, архивация

**Статус:** Принято

**Контекст:** `.context/decisions.md` эродировал: из 25 записей около трети — тактические фиксы, переименования и punch-list (ADR-002, 006, 008, 009, 011, 015, 017, 022); ещё 4 — развороты и отклонения без архивации (ADR-003, 004, 016, 021). Планка «что заслуживает ADR» неявно снижалась — пример ADR-022, где это признано прямо в тексте («граница „когда fix заслуживает ADR“ сдвинута к „фиксируем всё, что меняет поведение install.sh“»). В активном срезе плотность разворотов создавала впечатление колебаний, тактические ADR размывали ценность содержательных. Предыдущая попытка (ADR-004 «Управление ростом decisions.md через cc-architect-sync») принята, но не реализована.

**Решение:**

1. **Два уровня артефактов, единая дисциплина в мейнтейнерском и шаблонном слоях:**
   - **ADR** — `.context/decisions.md`, курируемые архитектурные решения, проходящие чек-лист.
   - **Commit messages** — всё остальное: тактические фиксы, переименования, cleanup. Отдельного operational-файла нет.

2. **Чек-лист ADR — gatekeeper `/record`. 4 пункта, ответ «да» на все — иначе commit:**
   - Рассмотрены альтернативы с содержательным разбором. Для решений «делать / не делать» — обоснование, почему выбрали именно этот вариант, а не противоположный.
   - Есть явный trade-off между альтернативами.
   - Решение формирует поведение продукта или процесса на длинной дистанции (≥ 6 месяцев).
   - Читателю через полгода без контекста будет полезно знать *почему*, а не *что*.

3. **Архивация разворотов и отклонений** в `.context/history/decisions/<year>.md`. Год — год написания ADR (сохраняет temporal context). Триггеры:
   - **X (реактивный):** новый ADR явно заменяет предыдущий → `/record` предлагает перенести старый в архив тут же.
   - **Y (периодический):** `/sync` проверяет активные ADR на статус «Отклонено» / «Заменено» без явной замены, предлагает архивировать.

4. **Маркер в шапке архивированного ADR:**
   - `> Заменено ADR-N (YYYY-MM-DD) — см. .context/decisions.md`
   - `> Отклонено (YYYY-MM-DD)`

5. **Конвенция ссылок** на архивированный ADR: `ADR-NNN (archived, see history/decisions/YYYY.md)`.

6. **Дисциплина commit-сообщений:** для нетривиальных фиксов — секция «Why» с коротким обоснованием. Косметические или refactor-без-содержания — без секции.

**Последствия:**

- **Замещает ADR-004 (archived, see history/decisions/2026.md)** — механика архивации теперь встроена в `/record` (X) и `/sync` (Y), scope шире.
- **Bulk-переклассификация 25 существующих ADR:** 13 остаются активными, 4 архивируются (ADR-003, ADR-004, ADR-016, ADR-021), 8 удаляются из активного корпуса (ADR-002, 006, 008, 009, 011, 015, 017, 022) — содержимое доступно в git-истории.
- **ADR-024 редактируется:** п.5 (правило bold-as-heading) убран, в «Последствия» добавлена ссылка «п.5 отменён ADR-025». Основная часть (режим `/polish --all`) актуальна.
- **Скиллы обновлены в обоих слоях:** `/record` с чек-листом, `cc-architect-sync.md` с шагом Y, `cc-commit.md` с конвенцией «Why».
- **`CLAUDE.md` в обоих слоях получает секцию «ADR discipline»** — 4-пункт чек-лист + ссылка на архив + конвенция ссылок.
- **`.context/history/decisions/`** становится реальной директорией с содержимым, а не placeholder.
- **Планка порога зафиксирована явно** — снижение планки без явного пересмотра дисциплины становится видимой ошибкой (не пройдёт чек-лист).

## ADR-025: Отмена правила «bold не должен использоваться как заголовок»

**Статус:** Принято

**Контекст:** Правило запрещало `**Метка:**` на отдельной строке в качестве псевдо-заголовка — введено в `CLAUDE.md` обоих слоёв и продублировано в `.claude/skills/project/rules/markdown-conventions.md` при первом наполнении polish rules (ADR-024 п. 5). Первый же прогон `/polish --all` показал 91 нарушение из 109 суммарных — паттерн де-факто прижился в ADR-записях, снапшотах статуса, скиллах, блюпринте. Ни один шаблон (`record.md`, `cc-status-report.md`) сам паттерн не предписывает — CC воспроизводит его при заполнении, потому что для лаконичной группировки внутри одного `##`-заголовка `**Метка:**` короче, чем плодить `###`-подсекции. Ужесточать шаблоны — растить их объём; переписать 91 существующее нарушение — переписывание истории без пользы. Само правило создавало шум, а не ловило реальные ошибки.

**Решение:**

1. **Удалить пункт правила из `.claude/skills/project/rules/markdown-conventions.md`** — переписать секцию целиком: убрать вхождение в списке правил, антипаттерн `**Section title**` на отдельной строке, добрый паттерн «bold только внутри предложения».
2. **Удалить строку «Do not use **bold** as a heading substitute…» из `CLAUDE.md` (корень) и `template/CLAUDE.md`.** Секция «Markdown conventions» в обоих файлах сокращается на один пункт; остальные (дефис-маркеры, языки у fences, пустые строки, `---` между major-секциями) сохраняются.
3. **Ретроактив не трогать.** 91 существующее нарушение не переписываем — история статусов и старые ADR остаются как есть.
4. **Шаблонной копии `markdown-conventions.md` нет** — правило в `template/` живёт только в `CLAUDE.md`. Асимметрию сохраняем.

**Последствия:**

- Заменяет часть ADR-024 п. 5: `markdown-conventions.md` описывает четыре пункта из пяти. Формулировка «никаких bold-as-heading» из ADR-024 устаревает.
- Будущие прогоны `/polish` перестают флагать `**Метка:**` — уменьшается шум.
- Конвенции в CLAUDE.md синхронизированы с polish-правилом — CC не получает противоречивые указания.
- Если позже возникнет более узкая проблема (bold как замена явного `##`-раздела на верхнем уровне) — вводится отдельное, точечное правило.

## ADR-024: Режим `/polish --all` — полный прогон по проекту без `simplify`

**Статус:** Принято

**Контекст:** ADR-023 п. 7 оставил кейс «вся ветка перед `/close`» отложенным. На практике возникает потребность прогнать `/polish` по всему коду проекта (не по diff): работа ведётся напрямую на `dev` без feature-ветки, готовится крупный релиз, накопились изменения от ручных правок вне обычного цикла `/dev`. Дефолтный diff-режим `/polish` (`merge-base HEAD dev..HEAD`) для этого не подходит — он ограничен точкой ветвления.

**Решение:**

1. **Аргумент `--all`** — новый режим `/polish`. Scope: все tracked-файлы (`git ls-files`), с необязательным исключением через `.polishignore` (формат совпадает с `.gitignore`). Файл не создаётся по умолчанию ни в мейнтейнерском, ни в шаблонном слое.
2. **В режиме `--all` встроенный `simplify` не вызывается.** Работают только project-rules из `.claude/skills/project/rules/*.md`. Причина: `simplify` рассчитан на diff, полнопроектный прогон даст шум и рискует превысить контекст. Это тот же fallback-режим «rules only», который уже описан в ADR-023 п. 2.
3. **Confirm перед запуском.** Показать количество файлов и приблизительный объём. Защита от случайного тяжёлого прогона.
4. **Пункт 3 ADR-023 (аргументы команды) расширяется** строкой `/polish --all` — «полный прогон по всем tracked-файлам, только project-rules».

**Последствия:**

- `cc-code-polish.md` в обоих слоях получает новую ветку алгоритма и confirm-шаг.
- Появляется опциональный `.polishignore` — контракт совпадает с `.gitignore`, отдельно не документируется.
- В шаблонном слое `.polishignore` по умолчанию не создаётся — пользователь заводит его сам при необходимости.
- Мейнтейнерский слой получает 2 живых правила — `markdown-conventions.md` и `no-placeholder-leaks.md`. Впервые задействуется точка расширения из ADR-023.
- **П.5 отменён ADR-025** — правило bold-as-heading исключено из `markdown-conventions.md`; остальные пункты правила актуальны.
- Если позже потребуется полнопроектный прогон с `simplify` — отдельный ADR.

## ADR-023: Команда `/polish` — пайплайн вычистки сгенерированного кода

**Статус:** Принято

**Контекст:** Между `/dev` и `/commit` нет инструмента вычистки сгенерированного кода. Встроенный в CC скилл `simplify` покрывает общие проверки (reuse/quality/efficiency), но не сочетается с проектными правилами. Дублировать функциональность `simplify` смысла нет; писать проектные правила «внутри» встроенного скилла невозможно. Нужен свой скилл-обёртка, который комбинирует встроенное с проектным.

**Решение:**

1. **Команда `/polish`** — новая слэш-команда в обоих слоях. Имя выбрано так, чтобы не пересечься со встроенными `/review`, `/simplify`, `/clean` — прецедент ADR-017.
2. **Скилл `cc-code-polish.md`** — обёртка (не замена): вызывает встроенный `simplify`, поверх применяет кастомные правила. Если `simplify` недоступен в версии CC — деградация до режима «только правила» с предупреждением.
3. **Аргументы команды:**
   - `/polish` — diff feature-ветки против точки ветвления (дефолт, post-`/dev` кейс)
   - `/polish <path>` — целевой файл или директория (on-demand)
   - `/polish --staged` — только staged-изменения
4. **Кастомные правила** — prose-файлы в `.claude/skills/project/rules/*.md`. Формат свободный: H1 (имя правила) + описание в свободной форме. Никакого YAML frontmatter, никаких обязательных секций, никаких severity-уровней. CC читает содержимое как контекст и применяет по существу.
5. **Discovery** — конвенционный: скилл сканирует `.claude/skills/project/rules/*.md` при запуске. Никакого конфига, никакой регистрации.
6. **`security-review` не входит в дефолтный пайплайн.** Отдельная задача, если понадобится.
7. **Кейс «вся ветка перед `/close`»** — отложен, отдельная задача.
8. **Оба слоя** — команда, скилл и директория `rules/` появляются и в мейнтейнерском, и в шаблонном слоях. Расхождение противоречило бы назначению фичи.

**Последствия:**

- Появляется 7 новых файлов (командные файлы, скиллы, `rules/`-директории с README и примером) и правки навигации в 5 существующих файлах — план в `.context/plan.md`.
- Директория `.claude/skills/project/rules/` в шаблоне становится точкой расширения проекта: пользователь добавляет `.md`-файл — правило подхватывается автоматически.
- Задача «Приоритет 3 → добавить `template/.claude/skills/project/`» из `to-do.md` закрывается этим ADR.
- Появляется явный контракт «prose-правила»: если позже потребуются severity/glob/auto-fix — отдельное обсуждение и отдельный ADR.
- Прецедент ADR-017 расширен: теперь избегаем не только конфликтов с существующими встроенными командами, но и с потенциальными (`/review`, `/simplify`, `/clean`).

## ADR-020: Явная языковая настройка в установщике и CLAUDE.md

## ADR-019: Добавить `/retro` как регулярный инструмент рабочего процесса

## ADR-014: Публикация как OSS — перевод, слэш-команды, демо

**Статус:** Принято

**Контекст:** Репо достигло состояния, пригодного для публикации как OSS-инструмента для сообщества CC-пользователей. Продукт — workflow-слой (скиллы, структура `.context/`, install/uninstall), не project starter с кодовым скаффолдингом.

**Решение:**

1. **Перевод на английский** — все файлы, которые видит пользователь: `template/CLAUDE.md`, `template/WORKFLOW.md`, `template/.claude/`, `template/.context/`, `README.md`, `SETUP.md`, `scripts/install.sh`, `scripts/uninstall.sh`.

2. **Слэш-команды вместо ключевых фраз** — естественные фразы (`обсудим`, `начинаем реализацию` и др.) ненадёжны: срабатывают случайно, непредсказуемы для нового пользователя. Заменить на детерминированные `/команды` через механизм CC slash commands.

3. **Демо** — GIF или скринкаст: одна сессия от `/architect` до `/commit`. Без демо незнакомый человек не поймёт ценность.

4. **README** — переписать с позиции нового пользователя: объяснить двухслойную структуру репо, показать что устанавливается через `template/`.

**Почему не Cookiecutter (отказ от ADR-003 (archived, see history/decisions/2026.md)):** продукт — workflow-слой, пользователь приходит со своим кодом. Code scaffolding — другой инструмент, не цель этого репо.

**Последствия:**

- ADR-003 (archived, see history/decisions/2026.md) переходит в статус «Отклонено»
- Задача Cookiecutter удаляется из `to-do.md`
- Мейнтейнерский слой остаётся на русском (внутренний инструментарий)

## ADR-013: Управление жизненным циклом ассистента — опциональные шаги install.sh и скрипт uninstall.sh

**Статус:** Принято

**Проблема:** `install.sh` всегда создаёт коммит и ветку `dev` — это мешает при установке в существующий проект. Нет способа удалить ассистента из проекта без ручной зачистки файлов, `.gitignore` и `.git/info/exclude`.

**Решение:**

1. **install.sh — опциональные коммит и ветка dev**: два отдельных вопроса с дефолтом `n`, задаются после вопросов о видимости ассистента. Если коммит=n и в репо нет коммитов — вопрос о ветке пропускается (ветку нельзя создать в пустом репо).

2. **scripts/uninstall.sh** — новый скрипт, доступный через curl. Алгоритм:
   - Проверить наличие `.git` в текущей директории
   - Показать список файлов/директорий ассистента, которые будут удалены
   - Спросить отдельно про `.markdownlint.json`
   - Запросить подтверждение
   - Удалить: `.claude/`, `.context/`, `CLAUDE.md`, `WORKFLOW.md` (и `.markdownlint.json` при согласии)
   - Вычистить блок `# workflow-template` до конца файла из `.gitignore` (если существует)
   - Вычистить блок `# workflow-template` до конца файла из `.git/info/exclude` (если существует)
   - Сообщить о результате; коммит оставить на усмотрение пользователя

**Последствия:**

- Установка в существующий проект стала полностью управляемой — пользователь сам решает про коммит и ветку
- Появился путь выхода: ассистент удаляется без следов через один скрипт
- `SETUP.md` обновляется: добавить раздел «Удаление»

## ADR-012: Улучшение install.sh — корректная работа с .gitignore и управление видимостью ассистента

**Статус:** Принято

**Проблема:** `install.sh` перезаписывает `.gitignore` при установке в существующий проект, уничтожая пользовательские исключения. Предупреждение о перезаписи расплывчато — не перечисляет конкретные файлы. Нет возможности скрыть присутствие ассистента в репозитории или коммитах.

**Решение:**

1. **Явный список перезаписываемых файлов** в предупреждении — статически, по текущему содержимому `template/` корневого уровня: `CLAUDE.md`, `WORKFLOW.md`, `.markdownlint.json`, `.claude/`, `.context/`. `.gitignore` указывается отдельно с пометкой «дополняется».

2. **`.gitignore` дополняется, не перезаписывается**: содержимое существующего `.gitignore` сохраняется, строки из шаблона добавляются с маркером `# workflow-template`, дубликаты пропускаются.

3. **Вопрос A — скрыть файлы ассистента из репозитория**: при `y` — `CLAUDE.md`, `WORKFLOW.md`, `.claude/`, `.context/` записываются в `.git/info/exclude`, а не в `.gitignore`. Причина: `.gitignore` коммитится и раскрывает присутствие ассистента маркером и содержимым; `.git/info/exclude` — локальный, в историю не попадает.

4. **Вопрос B — скрыть ассистента из сообщений коммитов**: при `y` — в `.claude/settings.json` добавляется ключ, отключающий Co-Authored-By (точное имя ключа уточняется при реализации).

**Последствия:**

- `install.sh` становится безопасным для установки в существующие проекты
- Пользователь явно управляет видимостью ассистента в репо и истории коммитов
- Ничто в закоммиченных файлах не раскрывает выбор инструментария при режиме скрытия

## ADR-007: Отказаться от init-project.sh в пользу install.sh

**Последствия:**

- Удалить `scripts/init-project.sh`
- Обновить `SETUP.md`: убрать «Способ 2: через клон», оставить только curl
- Проверить `CONTRIBUTION.md` на упоминания `init-project.sh`

## ADR-005: Добавить install.sh для установки через curl

**Статус:** Принято

**Связь с ADR-003 (archived, see history/decisions/2026.md):** ADR-003 планировал заменить `init-project.sh` на cookiecutter для поддержки стек-специфичных шаблонов. `install.sh` покрывает основной сценарий (публичное репо, без стек-специфики) без дополнительных зависимостей. ADR-003 откладывается до появления реального стек-специфичного кейса.

**Проблема:** Текущий процесс развёртывания требует клонировать workflow-template целиком, что загрязняет git-историю нового проекта клоном шаблона.

**Решение:** Добавить `scripts/install.sh` — скрипт, который скачивается через curl и устанавливает шаблон в свежий `git init`-репозиторий.

Механизм скачивания — tar.gz архив через GitHub:

```bash
curl -fsSL "${REPO}/archive/refs/heads/main.tar.gz" \
  | tar xz --strip-components=2 "workflow-template-main/template"
```

`--strip-components=2` убирает `workflow-template-main/template/` — файлы шаблона ложатся прямо в текущую директорию.

Сценарий для пользователя:

```bash
mkdir my-project && cd my-project
git init
curl -fsSL https://raw.githubusercontent.com/<GITHUB_USER>/workflow-template/main/scripts/install.sh | bash
```

**Разграничение скриптов:**

- `init-project.sh` — для мейнтейнера: запускается из клона репо, предполагает наличие `template/` рядом
- `install.sh` — для пользователей: скачивается через curl, работает в пустом `git init`

**Ограничения:** только публичное репо, всегда берёт `main`.

**Последствия:**

- `scripts/install.sh` добавляется в репо
- `SETUP.md` обновляется: оба способа установки документируются рядом
- GitHub username захардкожен в `install.sh` (читается из самого URL скрипта при `curl | bash` — можно не дублировать)

## ADR-001: Разделение мейнтейнерского и шаблонного слоёв

**Статус:** Принято

**Проблема:** Репо одновременно является местом разработки шаблона и самим шаблоном. Файлы документации (`docs/status.md`, `docs/plan.md` и др.) использовались и как живые рабочие документы мейнтейнера, и как шаблонные заготовки с плейсхолдерами — это конфликт.

**Решение:** Разделить на два независимых слоя в одном репо:

- Мейнтейнерский слой — корень репо: `CLAUDE.md`, `CONTRIBUTION.md`, `SETUP.md`, `docs/`, `.claude/skills/meta/`, `scripts/`.
- Шаблонный слой — папка `template/`: `CLAUDE.md`, `WORKFLOW.md`, `template/docs/` (с плейсхолдерами), `template/.claude/skills/meta/`.

Развёртывание нового проекта — через скрипт `scripts/init-project.sh`: интерактивно заполняет плейсхолдеры, перемещает `template/` в корень, удаляет мейнтейнерский слой, переинициализирует git, привязывает новый remote, делает init commit.

Мейнтейнерская шпаргалка по работе с репо — `CONTRIBUTION.md` (не копируется в новый проект). Шпаргалка для нового проекта — `template/WORKFLOW.md`.

**Последствия:**

- `docs/` содержит реальную документацию мейнтейнера, скиллы (cc-status-report и др.) работают корректно.
- `.claude/skills/meta/` и `template/.claude/skills/meta/` — независимые копии, расходятся по мере развития.
- `CLAUDE.template.md` переименовывается в `template/CLAUDE.md`.
- `SETUP.md` остаётся в корне как инструкция по развёртыванию (удаляется скриптом).
