# 2026-08-30 — Дисциплина ADR

## Триггер

Началось с идеи two-repo для OSS (публичный код + приватный AI-контекст). После разбора cwd-блокеров CC вышли на настоящую проблему: не «где прятать AI-контекст», а **почему его стыдно показывать**. Ответ — эрозия `.context/decisions.md`: тактические фиксы записаны как ADR, развороты не архивированы, планка «что заслуживает ADR» неявно снижалась (ADR-022 признаёт это прямо в тексте).

Стало ясно: two-repo был defensive-решением, скрывающим низкое качество контекста. Offensive-решение — сделать контекст портфолио-грейд через дисциплину курирования.

## Развилки и выборы

### 1. Сколько уровней артефактов

**Выбор:** 2 уровня (ADR + commit messages), единая дисциплина в мейнтейнерском и шаблонном слоях.

Отвергнут вариант с 3 уровнями (ADR + operational + meta): meta-работа специфична только этому репо, шаблон должен работать одинаково в обоих слоях.

### 2. Где живёт второй уровень

**Выбор:** commit messages. Отдельного `.context/operational.md` или `CHANGELOG.md` нет.

Отвергнуты:

- `.context/operational.md` — создаёт «облегчённый ADR», который со временем замусорится тем же способом.
- `CHANGELOG.md` — для user-facing релизов, не для internal decisions; преждевременно для проектов без релизного цикла.

Для findability тактических решений — `git log --grep` + дисциплина commit-сообщений с секцией `Why:`.

### 3. Чек-лист ADR (gatekeeper `/record`)

Четыре пункта, ответ «да» на все — иначе commit:

1. Рассмотрены альтернативы с содержательным разбором. Для «делать / не делать» — обоснование обеих сторон.
2. Есть явный trade-off между альтернативами.
3. Решение формирует поведение продукта или процесса на ≥ 6 месяцев.
4. Читателю через полгода без контекста будет полезно знать *почему*, а не *что*.

Пункт 1 смягчён от исходного «минимум 2 альтернативы» — для валидных случаев вида «отклонение фичи с содержательным анализом» (пример: ADR-010 отказ от template-mini).

### 4. Архивация

**Физическая структура:** `.context/history/decisions/<year>.md`, год написания ADR (сохраняет temporal context). Один файл на год, без индекса.

**Триггеры:**

- **X (реактивный):** в `/record`, если новый ADR явно заменяет предыдущий — старый переносится в архив сразу.
- **Y (периодический):** в `/sync`, ловит orphan-отклонения без явной замены.

**Маркер в шапке архивированного:** `> Заменено ADR-N (YYYY-MM-DD)` или `> Отклонено (YYYY-MM-DD)`.

**Конвенция ссылок:** `ADR-NNN (archived, see history/decisions/YYYY.md)`.

### 5. Переклассификация 25 существующих ADR

**Выбор:** bulk-переклассификация.

- **13 остаются активными:** 001, 005, 007, 010, 012, 013, 014, 018, 019, 020, 023, 024 (отредактирован), 025.
- **4 архивируются:** 003, 004 → `2025.md`; 016, 021 → `2026.md`.
- **8 удаляются из активного корпуса** (содержимое остаётся в git-истории): 002, 006, 008, 009, 011, 015, 017, 022.

Спорный случай — ADR-022 (retry в install.sh): borderline по чек-листу, но именно там документировано снижение планки. При новой дисциплине не проходит; retry описан комментариями в install.sh + git-истории коммита b05fb9f.

## Что не в scope этой задачи

Обсуждение обозначило смежные проблемы, вынесенные отдельно:

- Two-repo / submodule / overlay / wiki — публикация AI-контекста. Пока не блокирует; после наведения порядка в дисциплине может оказаться не нужным.
- `plan.md` как branch-local артефакт — уже в `to-do.md` как Приоритет 4.
- Ревизия `to-do.md` (тоже раздут и смешивает уровни) и `discussions/` (не архивируются) — сквозная проблема курации.
- `product.md` как отдельный артефакт (WHAT/WHY vs blueprint HOW) — может быть введён независимо.
