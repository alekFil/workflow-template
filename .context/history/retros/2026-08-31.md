# Ретроспектива 2026-08-31

**Период:** с предыдущего ретро (2026-06-21) до 2026-08-31. ~2 месяца, ~30 коммитов, 9 новых ADR (022-030).

## Что шло хорошо

- **Каскад самоусиливающихся решений (ADR-026 → 030).** Дисциплина ADR (026) → удаление status-архива (027) → Components vs дерево (028) → three-way split артефактов (029) → plan.md task-local (030). Каждое ADR строилось на предыдущем; ни одно не пересматривалось после принятия. Ясная архитектурная когерентность.
- **ADR-026 применён немедленно и bulk.** Не просто зафиксировали дисциплину — в тот же день переклассифицировали 25 существующих ADR (13 active + 4 archive + 8 removed). Чек-лист прошёл проверку на ADR-027 через 030 — ни один не оказался borderline junk.
- **Dogfooding работает.** ADR-030 (plan.md task-local) валидирован на собственной задаче: новый шаг `chore: clean plan.md` в `/close` успешно применён first-run — plan.md исчез с dev как естественный ретроактив, без ручных шагов.
- **Все три action items предыдущего ретро закрыты:** `/retro` синхронизирован в шаблон, «Тест install.sh» переехал в Приоритет 2, ADR-019 записан.
- **Ссылки через `(archived, see …)` держатся.** Ни одной broken-reference за 5 ADR-циклов — конвенция ADR-026 работает.

## Что было трудно

- **Blueprint.md дрейф — 2 месяца, 8 ADR.** До сегодняшнего `/sync` blueprint оставался на состоянии ADR-022; массовая переклассификация ADR-026 никак не отражалась. Регулярность `/sync` слишком низкая — приходится наверстывать 148-строчным refresh.
- **AI-auto-commit boundary crossing.** Пользователь заметил, что модель самовольно расширяла `/dev` шагом «предложи commit-сообщение и попроси подтверждения», де-факто частично исполняя `/commit` без явного вызова. Паттерн шёл незаметно много task-циклов подряд. Зафиксирован как Приоритет 4.
- **Two-repo идея — большое обсуждение без ADR.** Разобрали cwd-блокеры CC, альтернативы (submodule, per-branch ACL, overlay, wiki+MCP) — и вышли на переформулировку («настоящая проблема — качество AI-контекста»), что породило ADR-026. Продуктивно, но исходная two-repo модель осталась не-ADR, файл в `notes/`. То же с local LLM agent.
- **plan.md placement instability между ADR-029 и ADR-030.** Model делал мелкие ошибки — ссылки на discussions/adr-discipline после перемещения, чтение plan.md на dev. Стабилизировалось только с ADR-030.

## Паттерны и наблюдения

- **Все 8 новых ADR (023-030) — про сам workflow-template**, ни одного про целевые продукты. Это показатель зрелости: базовые кейсы шаблона покрыты, идёт refactoring собственной модели. Но одновременно — сигнал, что реального usage в external-проектах может не быть достаточно для калибровки.
- **User пресекает scope creep, model — расширяет.** Пример: попытка вести AI-обсуждения в `discussions/` до ADR-029; auto-commit в `/dev` до P4. Устойчивый workflow-паттерн — граница «команда не сползает в соседний скилл» держится плохо, требуется явный gatekeeping.
- **Cadence: 1 ADR каждые 1-3 коммита в последнем цикле.** Плотный поток архитектурных решений. Может стоить замедлиться после Приоритетов 1/2 — иначе демо и README откладываются каждым новым ADR (их придётся пересчитывать под изменившуюся модель).
- **Ретроактивы работают чисто.** Bulk-переклассификация ADR (026), удаление 14 status-архивов (027), git mv 5 discussion-файлов (029), удаление template/plan.md (030) — все прошли без потерь и без broken-references.
- **Приватность через `.gitignore` работает.** 4 AI-файла в notes/ реально приватны — не всплывают в git status, не попадают в чужие клоны. Модель ADR-029 → ADR-011 доказана практикой.

## Действия

- Приоритизировать демо-скринкаст + README-перезапись (Приоритет 1)
- Реализовать Приоритет 4 (устранить /dev → авто-commit)
- Зафиксировать частоту `/sync` — например, после каждых 3 ADR или после каждого закрытия Приоритета
- Оценить как ADR-кандидат: «Команда/скилл не сползает в соседний» — обобщение Priority 4
- Не-ADR наблюдение для мониторинга: проверить usage workflow-template в живых проектах, чтобы model refactoring не стал самоцелью
